Stage 0 · the words first

Nine terms. They're the whole system.

Social Reset is one loop with a crypto spine. Learn the names of the links and the loop explains itself. Tap any you're unsure about; leave the rest closed.

01Habit loop›

eli5The autopilot cycle — bored → open app → scroll → repeat — that makes you open Instagram before you even decided to.

preciseThe behavior engine detects loop signatures: repeated reopens, short sessions, unlock-then-instant-reopen. It scores 0–10 and picks the intervention level.

02Social Reset›

eli5The core trick: instead of "no, you can't have TikTok," the phone says "call your friend first." The unlock is earned by connection, not by willpower.

preciseA verified interaction with a trusted paired person → signed unlock grant → short-lived access → automatic relock. Pluggable via the ResetVerifier interface.

03AccessibilityService›

eli5The phone's watchdog that notices "YouTube just came to the front" — that's how the app knows a blocked app opened.

precisePrototype enforcement provider. Android docs stress it's meant for accessibility; UI-transition events + an overlay Activity are the v1 mechanism, with the limitation handled, not hidden.

04Enforcement engine · PolicyDecision›

eli5The traffic cop: every app-open gets one of three verdicts — let it pass, add friction, or demand a Social Reset.

preciseALLOW / FRICTION / SOCIAL_RESET, decided locally from Room-held BlockedApp + ScheduleRule rows plus the behavior score. Hard Mode leaves no bypass except configured emergency access.

05Trusted peer · Pairing›

eli5The one person whose "yes" counts. You two shake hands cryptographically once (QR or code), and after that their approval is provably theirs.

preciseShort-lived pairing session → public-key exchange → ECDH shared secret → HKDF purpose keys → user-confirmed fingerprint → persist only peer public key + metadata. Nothing secret ever stored in Room.

06Signed session events›

eli5Every step of the reset is a signed, numbered receipt — order matters, fakes get rejected, replays bounce.

preciseEach event carries protocol version, session id, monotonic sequence number, sender device id, event type, timestamp, nonce, optional payload hash, and signature. The verifier checks all of it before trusting anything.

07Unlock grant›

eli5A temp password with a stopwatch: valid only for you, only for that app, only for ~10 minutes — then it's worthless.

preciseSigned token bound to requester device, peer, session, package/policy, issue + expiry times, grant id, reset type. Replays, stale tokens, cross-device or cross-package tokens are all denied.

08Relay backend›

eli5A postman, not a judge — it ferries messages between the two phones but can never decide "you may unlock."

preciseFastAPI + SQLite + WebSocket. Stores device identity, pairing state, short-lived session coordination; relays signed events. The server literally cannot send an ALLOW_APP command — the phone validates everything itself.

09Fail closed›

eli5Any doubt = the phone stays locked. Bad signature? Locked. Server down? Locked. Weird timestamp? Locked. You can't trick your way in.

preciseBad signature, unknown peer, expired grant, replayed nonce, mismatched package, revoked relationship, invalid server response → deny. Meanwhile blocking itself fails open: no network still blocks.

Quick check before moving up
Why can't the server just send "unlock now" when the friend taps accept?

→ It's a relay, not an authority. The unlock only exists as a cryptographically signed grant the phone verifies locally — against its own policy, the peer's key, and the session's nonce/sequence. The server has no key that can mint one.

Stage 1 · the problem

Blockers treat you like a child. Willpower loses anyway.

Every screen-time app does one of two things: pure denial (frustrating, bypassed in a week) or shame (red streaks, guilt). Neither fixes the actual loop — you open the app to feel connected, even to a feed.

  • Denial fails — a block with a "5 more minutes" button isn't a block.
  • Shame fails — guilt is not a habit replacement.
  • Server-side blockers fail — offline = unprotected, and you trust a company with your usage.

Social Reset's answer: replace the dopamine hit with the real thing it imitates — another human. And make the unlock mathematically provable, so the app can't be sweet-talked.

The intervention screen never shames: "This looks like a habit loop. Instead of another scroll, connect with someone."

Stage 2 · how it works

First the whole system, with room to breathe.

Two phones and one dumb-but-honest postman. Your phone watches apps and enforces rules locally. The relay carries signed messages to your trusted person's phone. Their acceptance comes back as a signed grant your phone verifies before the lock ever opens.

① The app opens

AccessibilityService sees the package enter the foreground and hands it to the enforcement engine. Your schedule and blocked-app list live in Room on the phone — no server round-trip needed to decide anything.

② The engine judges

Local policy + a deterministic behavior score (reopens, short sessions, unlock-then-reopen) yield one verdict: ALLOW, FRICTION, or SOCIAL_RESET. Scores 0–2 pass lightly, 3–5 get friction, 6–10 demand a reset.

Weights are configurable defaults, not science — the point is determinism, not a model that can be gamed or hallucinated.

③ The reset begins

Requester mints a reset_session with a random id + nonce. The friend's phone gets a notification and accepts. Both phones exchange signed events — sequence numbers, timestamps, nonces — through the relay over WebSocket.

④ The grant is earned and verified

On verified completion, a signed unlock grant arrives — bound to device, peer, session, package, and expiry. The phone checks signature, nonce, sequence, timestamps, and target package itself. Anything off → stay blocked.

There is no code path from WAITING_FOR_PEER to UNLOCK_ACTIVE. And events are idempotent: replaying them can never mint a second grant.

⑤ Unlock, countdown, relock

Enforcement enters a temporary allow state with a countdown UI. When the grant expires, the app re-locks automatically — no button to extend, no negotiation.

IDLE → REQUEST_CREATED → WAITING_FOR_PEER → PEER_ACCEPTED → CONNECTION_ACTIVE → CONNECTION_VERIFIED → GRANT_ISSUED → UNLOCK_ACTIVE → EXPIRED → LOCKED (+ FAILED / CANCELLED → IDLE)
What if there's no internet — does blocking still work?
Yes — that's the "fail open for blocking, fail closed for unlocking" split. Rules, schedules, and decisions are all local, so blocks work offline forever. Only the social unlock needs the relay — and without it you simply stay blocked. No outage can free you, and no outage can trap your other apps.

Stage 3 · the hard edges

Where the real engineering lives.

1 · Fail closed — the security spine

Bad signature, unknown peer, expired grant, replayed nonce/sequence, wrong target package, revoked relationship, invalid server response — each one means stay blocked. The unlock path is the only path guarded this way; optional social niceties fail open.

This asymmetry is deliberate: the dangerous direction (getting in) must be provable; the safe direction (staying out) must be indestructible.

2 · Android won't make it easy

AccessibilityService is officially for accessibility, not app-blocking. Background activity starts and foreground services are restricted on modern Android. CallScreeningService can't prove a call was answered. On-device AI has inference quotas.

So CallAttemptVerifier is an experimental adapter that reports uncertainty — a mere dial never grants an unlock. Constraints are documented and handled, not assumed away.

3 · Crypto without ceremony

Per-device identity keys live in Android Keystore (via Tink) and never touch Room. Pairing = short-lived session + key exchange + ECDH/HKDF + a human-confirmed fingerprint. Every message is signed; every grant is bound and short-lived; ZXing handles the QR.

No custom crypto primitives — standard schemes through well-reviewed libraries only.

4 · What's actually proven (honest ledger)

  • Verified 2026-09-07, two emulators: paired via relay → live WebSockets → reset requested/accepted → grant issued + redeemed → blocked app opened during the window.
  • Unit-tested: coordinator flow, schedule matching, state machine, crypto, backend auth/relay/WS.
  • Not yet: QR pairing UX, release APK, reconnect/reboot/expiry/replay/revoke/permission-denial on real devices.

Say the next paragraph without looking and you can brief any engineer on Social Reset.

The 30-second version

"Social Reset is a two-phone Android wellbeing app. When a blocked app opens, an AccessibilityService hands it to a local enforcement engine that checks Room-held rules and a deterministic behavior score — and may demand a Social Reset: a verified interaction with a trusted paired person. The two phones exchange signed, sequenced, nonce-stamped session events through a FastAPI relay that can't unlock anything itself. A valid session yields a short-lived signed unlock grant the phone verifies locally — bound to device, session, package, and expiry — followed by a countdown and automatic relock. Security failures fail closed; blocking itself works fully offline. Verified end-to-end on two emulators; QR pairing and release hardening remain."

If a teammate pushes back

  • "Why not let the server unlock directly?" → The server has no signing power; grants are verified locally against policy + peer key. A compromised relay changes nothing.
  • "Can't the user just uninstall?" → v1 is honest friction for the user's own future self; Hard Mode removes bypass except configured emergency access. Android can't make uninstall impossible — nobody honest claims it can.
  • "What if the friend is asleep?" → Pending state, phone stays blocked in Hard Mode. The unlock requires a human, by design.
  • "Why deterministic scoring instead of ML?" → Explainable, offline, ungameable, and AI is explicitly subordinate to policy. It can be tuned, not jailbroken.
  • "Is a call enough to unlock?" → No — Android can't prove answered duration; the call verifier reports uncertainty and never grants on a dial.
